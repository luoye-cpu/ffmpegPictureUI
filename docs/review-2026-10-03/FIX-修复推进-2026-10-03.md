## 一、P0-2｜AVIF 增益图 `colr.full_range` —— 已验证关闭

### 1.1 修复内容（交接前已落地，本轮验证）
`src/FfmpegGui/Services/IsoBmffGainMapWriter.cs`：
- `Build(...)` 的 `baseFullRange` 默认值 `true` → **`false`**；
- `PatchColr` 改为**只读继承**底图原 `colr` 的 `full_range` 位（新增 `ReadNclxFullRange`），仅当底图无 nclx 型 colr 时才用兜底值；并把最终值回传，供 tmap 的 colr 对齐同一份像素。

### 1.2 验证方法
仓库内**没有**覆盖 AVIF 增益图**写出侧**的探针（现有 `verify-gainmap-isobmff.ps1` 只测**解码**侧）。故在**仓库外**建一次性验证工程
（`%TEMP%\p02verify\`，`ProjectReference` 指向本仓 `FfmpegGui.csproj`，用后即删），分两段取证：

- **A 段（单元级）**：反射直调 internal `IsoBmffGainMapWriter.PatchColr`，喂合成 `colr` 盒，看末字节。
- **B 段（端到端）**：真实 `ffmpeg(libaom-av1)` 编底图 + 产品 `GainMapEncoder.EncodeAsync(container:"avif")` 组装，静态扫描产物所有 `nclx` 盒。

### 1.3 实测读数（13 PASS / 0 FAIL）

```

A② 底图 colr=full(0x80)+兜底 false ⇒ 继承 0x80      PASS   ← "只读继承"是双向的
```

**变异验证**：把 `PatchColr` 的只读继承两行撤掉（`_ = ReadNclxFullRange(...)`，恢复"按兜底值硬写"）⇒
`A①` 转红（末字节 `0x80`）、`A②` 转红（末字节 `0x00`），`pass=3 fail=2`；原样改回 ⇒ 回 `5/5`。

### 1.4 独立对撞（用户提示：用本地 Google libultrahdr）
- **源码级权威口径**：`tools/src/libultrahdr/lib/src/avifultrahdr.cpp:435`
  `sdrNclx->full_range_flag = sdr_intent->range == UHDR_CR_FULL_RANGE ? true : false;`
  ⇒ 取**实际图像**的 range，与本次修复同向。（`:496` 同理管增益图。）
- **真实 AVIF Ultra HDR 样本**：`tools/src/libavif/tests/data/seine_{sdr,hdr}_gainmap_srgb.avif` 的 `nclx` 全为 `0x80` —— 它们是 **full-range 源**，与「随源而变」一致，不构成反例。
- ⚠ 本机 libultrahdr 的 `ultrahdr_app.exe`（`tools/src/libultrahdr/build/Release/`）**不含 AVIF/HEIC 编码器**（`-z x.avif` / `x.heic` 报 libheif `Unsupported file-type: Unspecified`；`-z x.jpg` 正常）。故 AVIF 侧只能用源码口径 + 样本比对做对撞，不能直接产出 AVIF。

### 1.5 附带澄清（本轮新增认知，别误记成缺陷）
产物里 **增益图自身**的 `colr` 是 `prim=2 trc=2 mtx=2 full_range=0x80`，**不是**本 bug 的残留：
写出器只重写底图 colr、并给 tmap 另加一条；增益图 item 的属性**原样保留**。而 ffmpeg 把增益图编成
`gray(pc, progressive)`（**full range**，实测日志），故 `0x80` 与它自己的编码**自洽**。

### 1.6 ✅ P0-2 的**永久锁**已补（`ServiceProbe avifgm`，见 §八）
本 bug 能溜进来，根因是**仓库内没有任何门禁覆盖 AVIF 增益图的写出侧**：
`verify-gainmap-isobmff.ps1` 只测**解码**（识别 `tmap` / 切增益图字节），`verify-gainmap-engine.ps1` 测引擎像素，
`ServiceProbe gainmap` 测 **JPEG** Ultra HDR 容器 ⇒ `IsoBmffGainMapWriter` 的 `colr` 处理**零判据**。
⇒ 已按本节的设想补上 `avifgm` mode 并接进默认清单（第 25 个），详见 **§八**。

### 8.4 两个顺带发现（本轮实测，登记以免误判）
1. **`artifact-sha16` 对 exe 是弱指纹**：`FfmpegGui.exe`(79,360 B)、`ServiceProbe.exe`/`UiTestHost.exe`/`GainMapTestHost.exe`(各 73,728 B)
   都是 **apphost**，**不随托管代码变化**（本轮给 `ServiceProbe` 加了 90 行代码，`ServiceProbe.exe` 的 sha16 仍是 `B90DBDE94BBA3C50`，
   变的只有 `ServiceProbe.dll`）。⇒ 轮里那条 `artifact-sha16` 里**真正标识产品代码的是 `FfmpegGui.dll`**（1,551,872 B），
   引用 exe 那一栏当"被测指纹"时要留个心。
2. **`pack.ps1` 之后 `src/FfmpegGui/bin/Release/…/FfmpegGui.exe` 会消失**（它走的是 `dotnet publish` **NativeAOT**，
   产物是 22.8 MB 的原生 exe，与 bin 里那个 79 KB apphost 不是同一个文件）⇒ 此时直接跑整轮会被 **STALE 闸**拒跑
   （`FfmpegGui.exe 不存在`）。⇒ **顺序必须是「先整轮、后出包」**；若出包后还要跑整轮，先重建四项目。
