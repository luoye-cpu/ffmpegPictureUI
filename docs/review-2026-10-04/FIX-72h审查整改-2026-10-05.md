## 1. F1 —— GUI 下拉此前完全无效（P0，本轮最重要）

### 1.1 缺陷链（实测 + 读码）
```
MainWindow.xaml : <ComboBox x:Name="RawColorTargetCombo">   ← 三项：rec2020 | auto | rec709
                  （**无** SelectedIndex 属性）
MainWindow.xaml.cs:536-543  → 8 个兄弟下拉逐个 SelectedIndex = 0
                            → **唯独漏了 RawColorTargetCombo**（全文 grep 确认）
MainWindow.xaml.cs          → **没有** RawColorTargetCombo.SelectionChanged（全文 grep 确认）
:2879 / :5864               → RawColorTarget = RawColorTargetCombo?.SelectedItem as string
                            → 无选中 ⇒ SelectedItem == null ⇒ RawColorTarget 恒 null
QueueProcessor.cs:666       → RawColorTarget ?? "rec2020"  ⇒ **永远走默认档**
```
**实测对照**：CLI `--raw-color-target rec709` **正常**（产物 ICC 原色 = BT.709，`redX=0.43604`；
默认档为 BT.2020，`redX=0.67348`）⇒ **缺陷只在 GUI**。这正是本仓最忌的「宣称≠交付」。

### 1.2 修法与它的**语义安全性**
- `SelectedIndex = 0` 指向 **`rec2020`**（XAML 首项）—— **正是产品默认档**（与 CLI 默认一致）
  ⇒ **不改变任何既有行为**，只让控件从"死的"变成"可用的"。
- `SelectionChanged += (_, _) => RegenerateCommand()` —— 与 `ColorRangeCombo` 等同款，
  保证改选后**命令预览刷新**。

### 1.3 为什么补**结构锁**而不是行为断言
本缺陷的本质是「**接线漏了**」，是结构问题：
① 静态可判、毫秒级、零成本；② 行为断言要驱动 GUI 下拉，成本高且易写成
"只验证控件存在"的**假绿**；③ 与 `_probe-geometry-single-source-scan` / `_probe-settings-clone-coverage` 同族。

## 2. F4 —— 新增门禁第 68 条 `_probe-gui-control-wiring.ps1`

**判据**：对 `MainWindow.xaml` 里**每一个** `<ComboBox x:Name="XCombo">`，
`MainWindow.xaml.cs` 必须存在 (a) 初始选中 **且** (b) 变更响应。

### 2.1 ⚠ 本锁开发期**自己踩的两个坑**（都记进注释，供后人）
1. **只认 `.cs` 直赋 ⇒ 把 21 个合法控件判红**（实测 `FAIL=12` 之后又 `FAIL=9`）。
   本仓有**三条**合法接线路径，**必须全认**：
   - ① `.cs` 直赋 `X.SelectedIndex =` + `X.SelectionChanged +=`（如 `FormatCombo`）；
   - ② **`FillComboByLoc(..., "XCombo", ...)`** —— 本地化下拉的初始化，其实现内 `combo.SelectedIndex = idx`
     （函数自陈「首次填充时 `ItemsSource` 为空 ⇒ XAML 里写的 `SelectedIndex` 已被重置为 -1」）；
   - ③ **XAML 属性** `SelectedIndex="0"` / `SelectionChanged="X_SelectionChanged"`（如 `ConversionModeCombo`）。
   ⇒ **「不得为绿而放宽」的另一面是「不得把对的判红」** —— 过严的假红同样是假读数。
2. **剥注释**：匹配前剥掉整行注释（`// …`），否则"注释里提一句"就能把文本锁喂绿（本仓真踩过）。

### 2.2 反控与点名锁（防本锁自己变成假绿）
- **反控**：白名单外的 combo 数 **必须 ≥ 8**（本仓实测 37）—— 掉了说明提取器空跑 ⇒ 判红。
- **点名锁**：`RawColorTargetCombo` 的 (a)/(b) **单独再锁一遍** —— 即使有人把它塞进白名单，也照样盯着。
- **fail-closed**：读不到 `MainWindow.xaml(.cs)` ⇒ **判红**（`PASS=0 FAIL=1`），不静默跳过。
- **自带汇总**（`PASS=n FAIL=m` + 断言驱动 exit）⇒ 不进 `$tableOnly` / `$noSelfSummary`。

## 3. F2 —— `rec709` 被静默丢弃（P1）

### 3.1 缺陷（实测）
`rawUserChoseTarget` 门（`:593-610`）挡住**整块**默认档逻辑，其中含 `rec709`（"强制 bt709 + sRGB，
覆盖容器能力"）。实测 `--raw-color-target rec709 --color-space sRGB` 的日志**只有**：
```
[RAW] 用户已指定目标色域（sRGB）⇒ 保留用户配置；输入声明已按线性中间件补齐为 bt2020/linear
```
—— **一个字都不提 rec709** ⇒ 用户以为生效了；且与 `CliParser` 帮助文本矛盾。

### 3.2 修法（**不改优先级**，只让冲突可见）
```
[RAW] ⚠️ --raw-color-target rec709 与显式目标色域**同时给出**：按「用户显式目标优先」处理
      ⇒ **rec709 本次不生效**（若确实要强制 bt709+sRGB，请**去掉**显式目标色域参数）
```
- **语义裁定**：用户显式目标优先（既有三轴设计**不动**）—— 只补**点名**，符合本仓「静默丢弃不点名」铁律。
- ⚠ **只 `rec709` 有冲突**：`rec2020` **就是**默认档（同值），`auto` 的作用域只在 TIFF 那条 SDR 例外档
  ⇒ 二者**不点名**（避免噪声；已用反向控制钉住）。

### 3.3 永久断言（加进第 67 条探针，共 3 条）
| 断言 | 作用 |
|---|---|
| 点名字样必须出现 | 静默丢弃 ⇒ 转红 |
| **反向控制**：用户显式目标仍优先 | 防止有人"改成 rec709 覆盖用户"来换绿 |
| **反向控制**：单独给 rec709 时**不得**出现误报告警 | 防噪声 |

## 10. H2 死后端 —— 已删除（2026-10-05，用户裁定）

### 10.1 裁定与修法
用户从三个选项中选定：**「把 H2 档改成显式『不支持』并删除该分支（最小、最安全）」**。
`ColorTransformPlan` 的 `else if (h2Possible && !needsGmo) { Backend = FfmpegFilter; … }` **整支删除**，
该情形如实落 `InProcess`（H1），日志不再声称 zscale。理由：
① 消除**记账不实**（此前日志写 `后端=H2(zscale…)`，实际是 H1 进程内算 —— 实测两者同时出现在同一份日志）；
② 消除隐雷：若日后有人给 H2 补执行体，**同一条计划会变成真缺陷**（H2 的 zscale **不做** BT.2100 HLG OOTF，
   而 H1 的 `Bt2100Ootf` 做 —— 两套算子口径分歧）。
③ 代价 = 失去"省进程"的**潜在**优化，但该优化**本来就没实现**（无消费者）⇒ 实际零损失。
