## 1. ICC fail-closed（第 2 项）

### 1.1 语义

`CarryIcc` 的前提是“源到底有没有 ICC”可判定，不能把“读不到”当成“源没有 ICC”。

三态 `SourceIccStatus { Absent, Present, Unreadable }` 已贯通：

- 探测侧：`ProbeInputColorMetadataCore` 在 exiftool 读取失败 ⇒ `Unreadable`；exiftool 可用且拿到描述符 ⇒ `Present`；exiftool 可用但没有 ICC 字段 ⇒ `Absent`；exiftool 不可用时走 `ProbeContainerIccPresence`（只判断容器里有没有 ICC，不解析）。
- **ICC 字段存在但解析失败**（空/过短/非法 profile）现在记 `Unreadable`，不记 `Absent`。这是本轮补上的关键分支，否则“有 ICC 但读不出”仍会被当成“没有 ICC”。
- 规划层：`PlanCarry` 在非 HDR 分支对 `Unreadable` 直接 Reject；HDR 分支仍可只继承 CICP，因为 ICC 本身没有 HDR 携带通路。
- 执行层：`QueueProcessor.RefuseCarryIccUnreadable` 在编码前拦截，写英文和中文两行日志，`item.ExitCode=90`，状态 `失败 (源 ICC 不可读)`，**零产物**。

### 1.2 实测

用 `tests/output/validate/caps/p3.png` 复制并替换 `iCCP` 数据为非法 profile，生成 `tests/output/_tmp/round-tmp/bad_icc.png`（PNG 仍可被 ffprobe 正常解码）：

```text
❌ [1/1] bad_icc.png → 失败 (源 ICC 不可读)
❌ [color] CarryIcc refused: source ICC presence is unreadable (exiftool missing or read failed); refusing to guess
❌ [color] 已拒绝：源 ICC 存在性不可判定（缺少 exiftool 或读取失败），不按 sRGB 猜测
═══ 队列处理完毕 — 完成 1 项, 失败 1 项
EXIT=1
```

- 输出目录无产物。
- 队列失败计数为 1；进程退出码非 0。
- `item.ExitCode=90` 是任务级码；headless 汇总仍按“任一失败 = 1”返回，因此进程级读数是 1，不是 90。若下游要求进程级 90，需要另外拍板聚合退出码口径，本轮未擅自改动。

### 1.3 exiftool 可运行性与 ICC 读取

三个既有问题在本轮被定位并修掉：

1. 打包的 58 KB `exiftool.exe` 可能缺 `perl532.dll`（code 126），旧逻辑只看文件存在就判可用。现 `TryUseCandidate` 必须通过 `-json -G -ColorSpace <exe>` 的自读验证才置 `_detectedPath`；失败只提示“不可用 + 原因”，按未安装处理。验证结果按路径缓存，`ClearCache()` 同步清空。
2. `ReadColorTagsOnceAsync` 的组合参数带 `-ProfileDescription`。对 JPEG 等没有该 tag 的容器，exiftool 返回 exit 1，导致整条合并探测被判失败、ICC 描述符恒为 null。已移除 `-ProfileDescription`；ICC 描述由 `IccProfileService.ExtractIccFromBase64` 从 ICC 头解析。实测 `src_photo.jpg` 走 `CarryIcc` 能读出 `sRGB/bt709 (ICC 识别, ICC curv[1024])` 并产出带 `iCCP` 的 PNG。

3. `GetCachedProbe` 直接把调用方给的路径交给 exiftool，而 exiftool 进程的 `WorkingDirectory` 固定在工具目录。调用方传仓库相对路径（ServiceProbe / 测试宿主）时，`File.Exists` 按进程 cwd 为真、exiftool 按工具目录找不到文件 ⇒ 合并探测 exit 1、ICC 描述符 null（`probe:wire` 的 F-12 就是这样红的）。现在 `GetCachedProbe` 先 `Path.GetFullPath` 锚定到调用方 cwd 再探测与缓存；`probe:wire` 复跑 **105 PASS / 0 FAIL**，F-12 合并描述符与两步法逐字段相等。

## 2. HDR / GainMap 输出语义（第 3 项）

### 2.1 结论

JPEG 的 GainMap 出口**物理上不是原生 PQ/HLG HDR**，而是“SDR 底图 + 增益图”。普通查看器只显示 SDR 底图，Ultra HDR 查看器才把增益图叠成 HDR。因此“HDR 输入 + 开启 GainMap 仍显示 SDR”不能简单归因于“没有自动输出 HDR”。

实际可达的成因是：旧 JPEG GainMap 默认只写 ISO 21496-1 APP2 + MPF，**没有写 XMP `hdrgm`**；不少 Ultra HDR 查看器只认 XMP，于是表现成“有增益图但不是 HDR”。

### 2.2 修复

`GainMapEncoder.ResolveMetadataForHdr`：

```text
HDR 源 + JPEG 出口 + 请求为默认 "iso" ⇒ "both"
```

即同时写 ISO 21496-1 与 XMP `hdrgm`；显式选 `xmp` / `both` 时不改写用户选择；AVIF/JXL 不升级（它们只有 ISO 承载）。

### 2.3 实测（HDR AVIF → JPEG + GainMap）

源：`tests/output/_tmp/hdr-jpeg-check-35c54947629b478baf9646519e3bec72/hdr-white.avif`
产物：`tests/output/_tmp/hdr-gm-latest-3a24f214d35b4842b07ffa82fb1aca4e/hdr-white.jpg`，3283 B，exit 0。


### 2.4 HDR → JPEG 不勾 GainMap

同一源、`--jpeg-gain-map false`：exit 0，产物 840 B。自动 Hable 映射执行；这不是黑图/空图。该产物只用于像素/尺寸核对，未把“肉眼看起来正确”写成色度测量结论。

### 2.5 HDR → AVIF auto

既有实测仍成立：输出 `yuv420p12le`、`color_range=pc`、`color_transfer=smpte2084`、`color_primaries=bt2020`，可承载 HDR 的容器保留 HDR。
