### 3.5 clap 裁切缺陷：根因、修法、影响面（2026-11-02）

**症状**：`tests/data/gainmap_hevc_16x16.heic`（1,523 B，Google libultrahdr 合成件）在
`ServiceProbe gainmap-stats` 上报「❌ 底图像素数 256（3072 B / 12）与探测尺寸 64x64（4096 像素）不符」
⇒ `decoded=null` ⇒ 产品静默退回 SDR。§3.1 第 3 条把它记成「16×16 太小」，**归因错误**（已在 §3.1 就地
追加更正条目，原句按 AGENTS §6 保留不改）。

**容器真值**（字节级实读）：
- `ispe` @1015 = **64×64**（编码尺寸）
- `clap` @1035，box size 40，`widthN/D = (16,1)` / `heightN/D = (16,1)`（可见区 16×16）
- ffprobe：`streams[0]` = 64/64，裁切在 `streams[0].side_data_list` 的
  `Frame Cropping{crop_bottom:48, crop_right:48}`；**`frames[0].side_data_list` 只有 `ICC profile`**
- 裸流 `gbrpf32le` 解出 3,072 B = 16×16×12 ⇒ 像素真值 16×16

**根因**：改动前的 `ImageGeometry` **根本不读任何裁切** —— `rg "Frame Cropping"` 在 HEAD 版 0 命中，
`BuildProbeArguments` 只请求 `frame_side_data_list`，**stream 侧 side data 连请求都没发**
（`git show HEAD:src/FfmpegGui/Services/ImageGeometry.cs:52`）。而本件的 `clap` 被 mov 解复用器暴露成
**流级** `streams[0].side_data_list` 的 `Frame Cropping` ⇒ 探测恒取 `coded` 64×64，与裸流 16×16 对不上
⇒ 对账式判「像素数据不完整」。

**修法**（有意**不新增第二份几何真值**，否则 `verify-geometry-single-source` 当场红）：
1. **先让 ffprobe 把流级 side data 报出来**：`BuildProbeArguments` 由
   `-show_entries stream=width,height -show_entries frame_side_data_list` 改为再串一条
   `-show_entries stream_side_data`（`ImageGeometry.cs:50-53`）。**这一步是前提**——少了它，下面六条
   全做完探测仍是 64×64。
2. 新增 `ReadFrameCropping(stream, …)`，**只从 `streams[0].side_data_list`** 取
   `side_data_type` 含 `Frame Cropping` 的那条，`cropX = l + r` / `cropY = tp + bt`，首条命中即 `return`
   （同层还挂着 `ICC Profile`，逐条扫键名会把无关数字当裁切量）。`frames[]` 层**不解析裁切** ——
   那层只由 `ReadRotation` 用来读 `displaymatrix`。
3. `ParseDisplaySize` 退化为 3 行薄壳 ⇒ `ParseDisplaySizeWithCrop` 返 `(w,h,cropX,cropY)`，
   `catch (JsonException) => (0,0,0,0)`。
4. `DisplaySizeWithCropAsync` 单点透传裁切量，`DisplaySizeAsync` 退化为薄壳转发 ——
   **裁切量**的唯一消费者是 `GainMapDecoder`；但裁切**扣减写在共用实现里**
   （`ImageGeometry.cs:102-107`），故 5 个走薄壳的调用点对带 `clap` 的文件**同样从小尺寸开始记账**
   （这正是修复的期望效果，见下表；「不变」只指它们拿不到裁切量、无从据此对账）。
5. **先裁后转**：裁切在 `ApplyRotation` 之前扣减（`ApplyRotation` 的结果改名 `fw/fh`，避开已占用的
   `dw/dh`，否则 `CS0136`）。依据：`asym.avif`（coded 64×48 + `crop_bottom 16` + `irot 1`）ffmpeg 出
   **32×64**；若先转后裁会得 48×64。

## 5. 环境陷阱（本会话实测，接手必读）

  `UnauthorizedAccess_IODenied_Path` ⇒ 跑 app 或探针前先
  `$env:TEMP=$env:TMP=$env:TMPDIR='C:\PLAN\ffmpegPictureUI\tests\output\_tmp\<名>'`（目录先建）。
- **web_search 429**（DeepSeek 端点限流，重试无效）；`web_fetch` 与 pwsh
  `Invoke-WebRequest` 可用；api.github.com 60 req/h 限流（403），raw.githubusercontent.com 不限。

- exiftool 对打包版 ffmpeg 探测报 `[dngtool] unknown option: --version`（无害噪声）。
- ffmpeg 对 tmap 派生项报 `Derived Image item of type tmap is not implemented` +
  `unsupported color_parameter_type rICC`：**非致命**，底图组解码照常（`[0:g:0]` 组流可用）。
- 临时变异臂（method=1 → `case 7`）已复原，复原后门禁复跑 92/0 确认——工作树无残留。

  导出树与工作树各跑一遍**同一套分桶器**得出的（`clap-e/cjk_attr_1102b.log` 里每棵树都带 `TOTAL … ui=` 行）。
  手数会漏掉「续行未接 sink ⇒ 落 UI 桶」这一类（本批 +1 正是这种形态）。
- **提交会改二进制指纹**：`ProductVersion` 带 `+<HEAD 全哈希>`（SDK
  `IncludeSourceRevisionInInformationalVersion` 默认开）⇒ **每次提交后重建，`FfmpegGui.dll` / `ServiceProbe.dll`
  的 sha16 必变**，哪怕源码一字未改。本批实测：整轮打在 `eff6e73`（`ProductVersion=1.6.0-beta10+eff6e73…`，
  dll `5FFF1FB9460C57C5` / `DE3672E8547085D7`），提交成 `46dc819` 后同源全量重建得
  `BE793E7962766052` / `057D94DCEA24EBD5`（`ProductVersion=1.6.0-beta10+46dc819…`）——两份二进制只差
  版本串里那 40 位。⇒ **记指纹必须同批记 HEAD 提交哈希**；只记 dll sha16 的读数，事后要复算得先
  `git checkout <那个提交>` 再重建。（同一提交内的增量重建仍是比特稳定的：变异 M 复原后重建两次都是
  `5FFF…`／`DE36…`，那是「未提交」状态下的复现。）
