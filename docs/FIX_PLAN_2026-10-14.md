## T2 — 发射收口 + 组形态换写

**现状（本会话回读更正）**：`AppendVideoFilter`（`:1956–1981`）三分支（既有 `-vf` / 既有 `-filter_complex`（插在 `,split` 前）/ 新建 `-vf`，新建点在 `:1980`）。
**但「新建 `-vf`」在全仓有 5 处，只有 1 处在这个 helper 里**（实测 `grep Add("-vf")`）：

| 行号 | 所属路径 | 组形态下的处置 |
|---|---|---|
| `:1980` | `AppendVideoFilter` 新建分支（色彩链，本次崩溃点） | 走 `AppendChain` 分叉 |
| `:348` | GIF 且 `GifPaletteOptimize==false` 支 | 与 `:343` 的带标签 `-filter_complex` 互斥支；组形态下必须并入链首 |
| `:373` | APNG 动画 `fps/scale` | 同上，改走 sink |
| `:409` | GIF→AVIF 的 `format=rgba,format=yuva420p` | 同上，改走 sink |
| `:456` | JXL 动画 `fps/scale` | 同上，改走 sink |

⇒ **只改 `AppendVideoFilter` 会漏修四条路径**（那四处会先建出独立 `-vf`，组形态照样 EINVAL）。

**改法**
1. 新增唯一 sink `AppendChain(List<string> args, string filter, bool groupDerived)`，**上表五个新建点全部经它**：
   - 既有 `-vf` 或既有 `-filter_complex` 的**追加分支语义不动**（iccgen 依赖「追加」语义，见 `:2074` 那段注释，禁止顺手统一）；
   - 只有「新建」这一步分叉：`groupDerived==false` ⇒ 仍写 `-vf`（**逐字不变**）；`true` ⇒ 写**无标签** `-filter_complex "<链>"`。
2. **形态一次定死**：同一命令行只能有一种形态。sink 内先看 args 里已有什么（`-vf` 或 `-filter_complex`），若已建 `-vf` 而本次判为组形态 ⇒ 必须就地改写为 `-filter_complex`（并点名改写），不许两种并存——否则谁先谁后取决于格式分支顺序，等于把这条缺陷藏在分支顺序里。
3. `groupDerived` 只由 T1 的 `TileGroupTiles > 1` 决定，**不看输出格式**（现有 GIF 先例 `:326–343` 把判据挂在输出格式上，是错的轴；它的带标签复合图形态原样保留，不要并进来）。

**判据（修复前必须红）**
- 形状判据：注入探针为真时，命令行**不得**出现独立 `-vf`，必须出现 `-filter_complex`；在未修态必红（真图实测：`Filtergraph 'iccgen' … Invalid argument`、rc=127、零产物）。
- 真图端到端（一次性，非注入缝）：分块 HEIC→WebP 出图且 `ffprobe` 尺寸=**5888×4416**。
- 中性对账（活臂，必须在非分块源上量）：`-vf` 与无标签 `-filter_complex` 同链产物**逐字节相同**（本会话实测 md5 `ecef5e523b03e005df7b0f31e0787477` 两份相同）⇒ 非组任务的命令行与产物都不许变。

**产物影响**：仅分块/组类源从「零产物」变「出图」。
**回退**：`AppendChain` 的新建分支改回恒 `-vf`（单点）。

## T3 — 组路径链首回灌标签（与 T2 同批）

**为什么必须同批**：组图的输出帧**只保住 range 与 matrix**，primaries 与 trc 被洗成 unknown（实测组路径 `yuvj420p(pc, smpte170m/unknown/unknown)`，而源 tile 流是 `pc / primaries=bt470bg / trc=iec61966-2-1 / matrix=smpte170m`）。凡依赖帧标签的滤镜（`zscale`、`iccgen`）在组路径上先天没有操作数——`zscale` 报 `code 3074: no path between colorspaces`。

**改法**：`groupDerived==true` 时，链首插
`setparams=color_primaries=<源探得>:color_trc=<源探得>:colorspace=<源探得>:range=<源探得>`，
取值来自裁决点/`ColorMetadata`（**不是**帧标签）。`setparams` 不动像素，只写标签。

**判据（修复前必须红）**
- 三元组对账：组路径链首加 setparams 后，`-f null` 的输出流标签必须等于源 tile 流读数（实测已成立：回灌后 `pc, smpte170m/bt470bg/iec61966-2-1`）。
- 牙：分块 HEIC 上跑 GainMap 的 `LinearDecodeFilter` 串，无回灌必 3074、有回灌必须出 `5888*4416*12` 字节的 raw（**注意**：本会话在 SDR 真图上跑该串仍需按 `npl/pin` 语义复核，见账本未证项；判据要绑在「3074 消失」而非「数值正确」）。
**产物影响**：仅组类源。
**回退**：关掉链首插串开关（单点）。

## T6 — iccgen 的操作数由应用写入（**已判定不做：两条前提被实测否证，且回退了一次自伤实现**）

> **2026-10-14 实测结论**（原文保留供追溯）：
> 1. 非组路径上 iccgen 并没有取错操作数 —— P3-iCCP PNG→png 的产物 iCCP 色度 = **(0.682, 0.3194)**，与源 ICC 逐维相等；输入侧 `-color_primaries/-color_trc` 声明**对无 VUI 的容器（PNG/JPEG）本来就有效**，被 VUI 顶掉只发生在带码流 CICP 的 hevc/h264 上。
> 2. 唯一证过的错标格（真图 HEIC）属**组路径**，已由 T3 链首回灌修掉；本机**没有**「非组 + nclx 与 ICC 互相矛盾」的样本 ⇒ 为其写触发条件等于凭推理改标签。
> 3. 自伤：`setparams` 的 `colorspace` **不接受 `rgb`**（`Undefined constant … in 'rgb'` ⇒ `Invalid argument`、零产物），而我按 RGB 原生格式拼了 `colorspace=rgb` ⇒ 在 PNG 格上误触发并打断命令。"帧标签 unknown 就视作不可用并插入"也是错判据（unknown 时声明已生效）。
> 已回退：iccgen 发射点的插入、`IccgenOperandReset`、`ColorMetadata.rawFramePrimaries/rawFrameTrc`（`git diff` 现无 T6 痕迹；build 0/0、锁 PASS=5/0、`verify-decision-delivery` 与 `_probe-jpg-p3-icc` 各 rc=0）。
> **将来若拿到该形态样本**：触发条件限定为「原始帧标签**可用**且与声明不同」，且只发 `color_primaries/color_trc`（**不发 colorspace**），并先确认容器不是 RGB 原生。

**分歧事实**：手机 HEIC 常是「colr 挂 P3 ICC + nclx/VUI 标 bt470bg/smpte170m」的自相矛盾体；ffmpeg 只认 VUI，且输入侧 `-color_*` 声明对带 VUI 的 hevc/h264 **是空转**（实测声明与不声明同哈希；活臂只能用无标签 rawvideo 源）。`iccgen` 读帧标签 ⇒ 对本例产出 **sRGB/709 色度** ICC（0.6484,0.3309 / 0.3212,0.5979），贴到未改动的 P3 像素即错标签。

**改法**：只在「源有 ICC 且 ICC 探得空间 ≠ 帧 VUI 标签」时，把 T3 的 `setparams` 同样施加到**非组路径**的 iccgen 前（同一个具名入口，不许第二套公式）；并在日志点名「iccgen 的操作数已由源 ICC 覆盖帧标签」。

**判据（修复前必须红）**
- 生成 ICC 的色度必须与源 ICC 逐维相等。取数配方（本会话跑通）：出口选 PNG（iCCP 一定落盘）→ `PIL` 读 `info['icc_profile']` → 解 `rXYZ/gXYZ/bXYZ` 的 `s15Fixed16` → `x=X/(X+Y+Z)`；期望 `(0.682,0.3194)/(0.2845,0.6746)/(0.1559,0.0661)`。**解析器定锚**：`iccgen=color_primaries=smpte432:color_trc=iec61966-2-1` 那臂与 exiftool 抽出的源 ICC 逐维相等，两路独立同值。
- 未修态该判据必须读到 sRGB 色度（实测已成立）。

**产物影响**：iccgen 真落盘的三格（png/jpg/tiff）iCCP 字节变化（像素不变）⇒ 依赖该字节的逐字节对拍与 PSNR 基线要重定。
**回退**：条件不成立时不插串（单点开关）。

# T12 全面实现规划：增益图输入的"配对保全"架构（计划，未开工）

## 根因重新定性（这一步改变了方案）

现状链路：`源 SDR + 增益图` →（解码）→ `线性 HDR PFM` →（`GainMapEncoder` **自造** Reinhard 底图）→（再导出增益图）。
这条链对**目标本身就是真 HDR**（AVIF/HEIC PQ·HLG、16-bit PNG）是对的；但对**目标又是增益图容器**（JPEG UltraHDR / AVIF tmap）时，它做了两次多余的往返：

- 底图被换成我们自己重定调的那一张 ⇒ 实测各段都变亮（shadow ×1.2165 / mid ×1.1409 / mid+ ×1.1520 / high ×1.0753，全图均值 **127.79 → 145.15**）；
- 而 `maxLog2Gain = log2(max(headroom,1))`（`GainMapEncoder.cs:131-136`）+ 「Reinhard 保证增益 ≥ 1」（`:347`）⇒ 新底图对任何像素都**不暗于**新 HDR，`minContentBoost` 恒 1 ⇒ 源声明的 `0.891×` 暗部端点**在结构上无法表达**。

⇒ 这不是某处漏了一个钳制，是**出口形态选错了**：对增益图→增益图的转换，应该**保住 (底图, 增益图) 这一对**，而不是把它熔成线性 HDR 再重铸。

## 决策（范围我自己定死，不再回抛）

引入**三形态出口选择器**，按"目标能否承载标准增益图 + 源是否本身就是增益图对"分派：

| 形态 | 触发条件 | 做法 | 保住什么 |
|---|---|---|---|
| **A 配对重封装 repackage** | 源有 (base,gain,params) **且** 目标能装标准增益图（jpg / avif） | 底图 = **源底图**；增益图 = **源 mask**；metadata 由厂商字段**翻译**成 ISO 21496-1（min/max/γ/offsets、channels=1、map 尺寸 1/2 合法直接用） | **双端点**（min<1 可写）、底图零漂移 |
| **B 线性 HDR 重建**（现路） | 目标为真 HDR（PQ/HLG、16-bit） | 走 `DecodeToLinearRawAsync`，底图由 tone map 决定 | 全信号 HDR；min 带语义上不需要，但**必须播报** |
| **C 纯 SDR 降级** | 目标装不下增益图（webp/png8/tiff…） | 现 tone map 路 + 降级码 | 只是不谎报 |

**范围限定（关键）**：A 只对"输入自带增益图对"生效（厂商尾注 / ISO `tmap` / UltraHDR JPEG）。**PQ·HLG 输入的 B 路一行不动** ⇒ 自家标准件产物必须**逐字节不变**，这是本规划唯一的硬安全网。

## T12 审查结论（同轮自查，7 条，其中 3 条改方案）

1. **改方案｜起手顺序错了。** 我上一轮建议"R4→R2→R3"。错：R4（JPEG→JPEG 字节复制）对**厂商 HEIC→JPEG** 并不独立——厂商 mask 不是 ISO 载荷，必须先有 R1 的字段翻译 + R2 的**写出侧支持 `min<0`**，否则复制出来的 APP2 仍声明 `minContentBoost=1`，带照样丢。正确顺序 **R1 → R2 → R4 → R3 → R5 → R6 → R7**。
2. **改方案｜A 路"零重编码"只对一种容器成立。** `IsoBmffGainMapWriter.Build(baseBytes, gmBytes, …)` 要的是 **AVIF/av01 字节**，而源底图是 HEVC tile grid ⇒ AVIF 目标必然重编码。文档里"同质量档可零重编码；需重编码时按所选档位"这句是含糊话，必须按容器拆开写明：**JPEG→JPEG = 可字节复制；→AVIF = base 必重编码、mask 可原样搬运（JPEG 子图→AV1 单声道 intra 仍需一次编码）**。
3. **改方案｜A 路会绕过单一裁决点，这是架构违规。** 本仓色彩决策已收敛到 `DecideOutputColor` 单一裁决点（步骤 3 的成果），而 passthrough 若直接写文件就**跳过裁决点**，与 `--color-space` / `--bit-depth` / `--color-tone-map` / 携带策略全部脱钩。必须定义：A 路仍走裁决点，只是裁决输出多一种"重封装"动作；且当用户显式要求与 passthrough 矛盾（例如选了 `--color-space sRGB` 又要保源底图）⇒ **点名冲突并按用户显式意图走 B/C**，不许静默择一。
4. **回归面低估。** 把"SDR ⇒ 不写增益图"的守卫从 `maxLog2Gain<=0` 改成"区间宽度为 0"，会让**纯衰减型**件（`max≤0`）也开始写增益图 ⇒ 直接影响 `GainMapEncoder.cs:738` 那条既有播报及其门禁期望。开工前要先把受这条影响的断言列出来（不是"大概 140 条"这种含糊话）。

### 审查抓到的读侧缺陷（已修）

**症状**：`ref_xmp.jpg` 是规范形状（主图 XMP 只有 `hdrgm:Version`，九项在次图 XMP），
自家解码器把它当普通 JPEG：输出 PNG **53120 B**（SDR），日志无 `[GainMap解码]`。
我们的 `our_xmp` 当时把九项也写进主图，所以从没暴露；这属于"自家产物自证"的盲区。

**机制**：`GainMapDecoder.ReadMetadataJsonAsync` 调 exiftool 时没有 `-ee`，exiftool 只读主图 XMP；
主图只有 Version ⇒ `GainMapMax` 等必填字段缺失 ⇒ `ReadMetadataAsync` 返回 null ⇒ 走 SDR。

**修法（两处，互相锁住）**：
1. 写入侧改成参考形状：主图 XMP = `Version` + `Container:Directory`；次图 XMP = 九项全量
   （`GainMapEncoder.BuildXmpMetadata` 的 `withDirectory` 分支）。
2. 读取侧 exiftool 加 `-ee`，并在 JSON 返回多个对象时选带 `GainMapMax` 的那个；
   XMP-only 的通道数仍由增益图 image 推断（ref_xmp 为 3，与参考默认 `-M 1` 一致）。
修复后 `ref_xmp` → `元数据来源: hdrgm XMP`、`✅ HDR 线性像素 512x384 峰值…`、PNG **117451 B**。

**新增门禁（锁住这条链）**：
- engine §1d：iso/xmp/both 三档产物全部回解，来源必须分别命中 ISO / hdrgm XMP / ISO+XMP，
  且日志出现"已解码为线性 HDR PFM"；负控 = 同输入不写增益图的普通 JPEG 不得出现来源行。
- engine ⑤b：主图 XMP 必须只有 `Version`、无数值（防再次"多写掩盖"）。
- thirdparty D5f：不带 `-ee` 只见 Version、带 `-ee` 见数值（证明元数据在次图 XMP 的规范位置）；
  D5/D5d 同步改用 `-ee`。

### 其他参考实现差异（合法，不动）

- 参考 ISO-only 件 `--useBaseColorSpace 0`（增益图在 alternate 空间）；本实现恒为 1（底图空间）。
  两者都把该标志写进 ISO flags，消费者按声明施加即可。
- 参考 `offsetSdr/offsetHdr = 0`；本实现 1/64（规范默认值）。本实现"声明 == 施加"由同一对常量保证。
- 参考 XMP 的 max 保留更多小数（49.2612 vs ISO 49.2611）；本实现两处都按 log2 两位小数写，同源一致。
- 参考 XMP-only 无 ISO 命名空间、ISO-only 无 XMP 命名空间；本实现三档同此（指纹矩阵锁住）。
