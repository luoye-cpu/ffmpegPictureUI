## 1. 现状：ACR 路线只覆盖 DNG

| 输入 | 当前解码臂 | 是否施加 OpcodeList1/2/3 | 渲染空间 |
|---|---|---|---|
| `.dng` | `dngtool -rdp`（Adobe DNG SDK 的 `dng_render`） | **全施加** | `srgb`（bt709 出口）/ `rec2020`（其余） |
| `.arw` `.cr2` `.nef` … | LibRaw（`dngtool -d`，2026-10-26 起固定恒等 gamm ⇒ 真线性 16-bit） | **一张都不执行** | 源相机空间，下游 zscale 转 |

结构性原因不是实现偷懒，而是 **Adobe DNG SDK 只读 DNG**：`dng_render` / `dng_negative` 的入口是
`dng_file_stream` 读 TIFF 结构，ARW/CR2/NEF 的容器与（更重要）**厂商私有 opcode 语义**它一概不认。
所以「让 ARW 也走 ACR」在 SDK 侧没有直接入口。

## 2. 两条候选链

**链 A（现行）**：RAW → LibRaw → 线性 16-bit TIFF → 下游。
优点：一步、快、已经在产品里跑了很久。缺点：opcode（暗角/畸变/CA 校正，即厂商写在 RAW 里的「拍摄后处理」）
全部不施加，与 Lightroom/ACR 的成像必然分叉。

**链 B（本文件要论证的「全量」）**：RAW → **LibRaw 解包 → CFA DNG（`dngtool -e`）** → `dngtool -rdp` → 线性 16-bit TIFF。
把 SDK 喂它认识的容器，代价是多一轮「写 DNG + 读 DNG」。

`dngtool -e` 的能力边界（`dngtool` 无参打印的用法串，2026-11-01 读取）：

- 默认写 **CFA** DNG（`-linear` 才是「无 CFA / 已去马赛克」的线性 DNG）⇒ 链 B 的中间件保得住传感器平面；
- 默认压缩是 **lossless JPEG**（`-lossless` 亦是无损）⇒ 中间件理论上逐位可逆；
- `-embed-raw` 自 2026-10-19 起**默认关**（不嵌原件），`-no-raw-meta` 可进一步剥掉 EXIF 搬运与预览；
- `-lens-corr` 默认关（它会把源 RAW 自带的镜头三表转成标准 OpcodeList3，**改渲染像素**）。

⇒ 链 B 的中间件生成必须**显式选边**：带不带 `-lens-corr` 会得到「opcode 已规范化进 DNG」与
「opcode 仍在厂商私有标签里、SDK 看不见」两种完全不同的成像。这是设计上第一个必须拍板的岔口。

## 3. 三个必须先证伪的风险（本批的探针就是打这三个）

**R1 中间件是否保真**。若 `-e` 的 CFA 平面与源 RAW 的解包结果不是逐位相同（例如隐式套了曲线、
或黑电平被重标定），链 B 的一切读数都建立在一个已经被改过的源上，与链 A 的差异就归因不清。
判据形状：同一 DNG 走 `-e`（lossless）再 `-rdp`，与直接 `-rdp` 原件**逐像素全等**。

**R2 中间件是否仍是 CFA**。`-e` 若在某种输入上退化成 `-linear`（无 CFA），`-rdp` 的去马赛克就不会发生，
产物是「把已去马赛克的图当 CFA 再插值一次」——看起来正常、细节全错。判据形状：中间件的
`PhotometricInterpretation` 必须是 CFA（32803）且 `CFARepeatPatternDim` / `CFAPlaneColor` 在场。

**R3 代价能否接受**。链 B 多一轮编解码。第 79 条已登记的边界是「`-rdp` 耗时约为 LibRaw 的 2.2×
（24MP 5.1 s vs 2.3 s）」，链 B 要在它之上再加一次 `-e`。预算必须是**量出来的倍数**，
不能写「感觉还行」。

## 4. 设计取舍（本批只记录，不实施）

1. **默认路由不动**。链 B 会让所有非 DNG 输入的像素改变（opcode 开始施加、渲染空间开始按下游目标选），
   属产品行为变更，需要单独一轮的像素读数与用户可见说明。
2. **岔口「opcode 从哪来」取「源自带」而非「我方规范化」**：链 B 的价值就在于让 ACR 的成像与
   Lightroom 对齐，而 Lightroom 施加的是**源 RAW 里的厂商 opcode**。所以中间件生成**不加** `-lens-corr`
   （那是把镜头表**翻译**成标准 opcode，属另一件事，已在第 79 条 ⑱ 单独锁）。
   ⚠ 但这留下一个已知缺口：**厂商私有 opcode 不是标准 OpcodeList**，LibRaw 解包后它们就丢了
   ⇒ 链 B 在非 DNG 源上**拿不到**真正的 ACR 成像，只能拿到「CFA 平面 + Adobe 的通用水面」。
   这条缺口是链 B 的**上限**，不是 bug；要闭它必须解析各厂私有块（Sony 的 0x7032/0x7035/0x7037
   已被 `-lens-corr` 覆盖，其余厂没有）。
3. **失败回退**：`-e` 或 `-rdp` 任一失败就回 LibRaw 是**错误**的默认——两条臂的成像不同，
   静默换臂等于「这批产物有的施加了 opcode、有的没有」，且日志里看不出来。应**拒绝并点名**。
4. **中间件落地**：若将来实施，必须落 `tests/output/<组名>/<run>/`（GUID 轮次目录，AGENTS §3），
   不许进 `%TEMP%`，也不许与产物同目录混放（`-e` 的产物与最终产物同名段会互相覆盖）。
